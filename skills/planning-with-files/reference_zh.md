# 参考：Manus 上下文工程原则

本技能基于 Manus 的上下文工程原则，该公司于 2025 年 12 月被 Meta 以 20 亿美元收购。

## 六大 Manus 原则

### 原则一：围绕 KV 缓存进行设计

> “KV 缓存命中率是生产级 AI 智能体唯一最重要的指标。”

**统计数据：**
- 输入与输出令牌比例约为 100:1
- 缓存令牌：$0.30/百万令牌 vs 未缓存：$3/百万令牌
- 成本相差 10 倍！

**实施方法：**
- 保持提示前缀**稳定**（单个令牌的更改会使缓存失效）
- 系统提示中**不要**包含时间戳
- 使上下文**仅可追加**，并采用确定性序列化

### 原则二：掩码，而非移除

不要动态移除工具（这会破坏 KV 缓存）。应改用对数概率掩码。

**最佳实践：** 使用一致的动作前缀（例如 `browser_`、`shell_`、`file_`）以便于掩码。

### 原则三：文件系统作为外部存储器

> “Markdown 是我磁盘上的‘工作记忆’。”

**公式：**
```
上下文窗口 = 内存（易失、有限）
文件系统 = 磁盘（持久、无限）
```

**压缩必须可恢复：**
- 即使丢弃网页内容，也要保留 URL
- 丢弃文档内容时，保留文件路径
- 绝不丢失指向完整数据的指针

### 原则四：通过复述操控注意力

> “在整个任务过程中创建和更新 todo.md，以将全局计划推入模型的近期注意力范围。”

**问题：** 经过约 50 次工具调用后，模型会忘记原始目标（“迷失在中间”效应）。

**解决方案：** 每次决策前重新读取 `task_plan.md`。目标会出现在注意力窗口中。

```
上下文开始：[原始目标 - 遥远，被遗忘]
...多次工具调用...
上下文结束：[最近读取的 task_plan.md - 获得注意力！]
```

### 原则五：保留错误内容

> “将错误的尝试留在上下文中。”

**原因：**
- 带有堆栈跟踪的失败操作让模型能够隐式更新信念
- 减少重复犯错
- 错误恢复是“真正智能体行为最清晰的信号之一”

### 原则六：避免陷入少样本陷阱

> “一致性滋生脆弱性。”

**问题：** 重复的动作-观察对会导致漂移和幻觉。

**解决方案：** 引入受控的变化：
- 略微改变措辞
- 不要盲目复制粘贴模式
- 在重复性任务上重新校准

## 三大上下文工程策略

基于 Lance Martin 对 Manus 架构的分析。

### 策略一：上下文缩减

**压缩：**
```
工具调用有两种表示形式：
├── 完整：原始工具内容（存储在文件系统中）
└── 紧凑：仅引用/文件路径

规则：
- 对陈旧（较旧）的工具结果应用压缩
- 保持近期结果完整（以指导下一个决策）
```

**摘要：**
- 当压缩效果递减时应用
- 使用完整的工具结果生成
- 创建标准化的摘要对象

### 策略二：上下文隔离（多智能体）

**架构：**
```
┌─────────────────────────────────┐
│         规划智能体              │
│  └─ 将任务分配给子智能体       │
├─────────────────────────────────┤
│       知识管理器                │
│  └─ 审查对话                   │
│  └─ 决定文件系统存储           │
├─────────────────────────────────┤
│      执行子智能体              │
│  └─ 执行分配的任务             │
│  └─ 拥有自己的上下文窗口       │
└─────────────────────────────────┘
```

**关键见解：** Manus 最初使用 `todo.md` 进行任务规划，但发现约 33% 的操作都花在更新它上面。后来转向由专用规划智能体调用执行子智能体。

### 策略三：上下文卸载

**工具设计：**
- 总共使用少于 20 个原子函数
- 将完整结果存储在文件系统中，而非上下文中
- 使用 `glob` 和 `grep` 进行搜索
- 渐进式披露：仅在需要时加载信息

## 智能体循环

Manus 在一个连续的 7 步循环中运行：

```
┌─────────────────────────────────────────┐
│  1. 分析上下文                          │
│     - 理解用户意图                      │
│     - 评估当前状态                      │
│     - 审查近期观察结果                  │
├─────────────────────────────────────────┤
│  2. 思考                                │
│     - 我应该更新计划吗？                │
│     - 下一个逻辑动作是什么？            │
│     - 是否存在阻碍？                    │
├─────────────────────────────────────────┤
│  3. 选择工具                            │
│     - 选择一种工具                      │
│     - 确保参数可用                      │
├─────────────────────────────────────────┤
│  4. 执行动作                            │
│     - 工具在沙箱中运行                  │
├─────────────────────────────────────────┤
│  5. 接收观察结果                        │
│     - 结果追加到上下文中                │
├─────────────────────────────────────────┤
│  6. 迭代                                │
│     - 返回步骤 1                        │
│     - 持续直到完成                      │
├─────────────────────────────────────────┤
│  7. 交付结果                            │
│     - 将结果发送给用户                  │
│     - 附加所有相关文件                  │
└─────────────────────────────────────────┘
```

## Manus 创建的文件类型

| 文件 | 用途 | 创建时机 | 更新时机 |
|------|---------|--------------|--------------|
| `task_plan.md` | 阶段跟踪、进度 | 任务开始时 | 完成阶段后 |
| `findings.md` | 发现、决策 | 任何发现后 | 查看图像/PDF 后 |
| `progress.md` | 会话日志、已完成事项 | 在断点处 | 整个会话期间 |
| 代码文件 | 实现 | 执行前 | 出错后 |

---

## 关键约束

- **单动作执行：** 每轮一次工具调用。无并行执行。
- **计划是必需的：** 智能体必须始终知道：目标、当前阶段、剩余阶段
- **文件即记忆：** 上下文 = 易失。文件系统 = 持久。
- **绝不重复失败：** 如果动作失败，下一个动作**必须**不同
- **通信是一种工具：** 消息类型：`info`（进度）、`ask`（阻塞）、`result`（最终）
